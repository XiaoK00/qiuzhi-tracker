# 求职投递追踪器

将包含本文件的目录记为 `<skill-dir>`。

## 核心原则

工作簿用于帮助用户快速判断三件事：

1. 这个岗位现在能不能投。
2. 这个岗位是否值得投。
3. 下一步具体做什么。

只有会改变投递判断、优先顺序或下一步行动的信息，才设置为独立列。检索底稿可以保留在结构化 JSON 中，但不得把所有研究字段重复搬进 Excel。

企业池与岗位清单必须分工：

- **企业池**管理公司，一家公司原则上一行。
- **岗位清单**管理具体招聘机会，同一公司可有多行。
- 两张表正常重复的核心字段只有企业名称。
- 企业行业、规模和企业风险不在岗位清单重复。
- 具体岗位要求、截止日期和契合指数不在企业池重复。

## 必须使用的资源

开始任务后按需读取：

- 建立或更新工作簿前，读取 `<skill-dir>/references/workbook-schema.md`。
- 联网检索和状态判断前，读取 `<skill-dir>/references/research-rules.md`。
- 计算契合指数和当前行动前，读取 `<skill-dir>/references/matching-rubric.md`。
- 新建工作簿时，优先复制并编辑 `<skill-dir>/assets/qiuzhi-tracker-template.xlsx`。
- 将企业池和深度核验岗位保存为一个 JSON 文件，并在写入 Excel 前运行：

```bash
python <skill-dir>/scripts/validate_tracker_data.py <tracker-data.json> \
  --min-companies 100 --min-jobs 30 --normalized <normalized.json>
```

用户要求的数量不同时，调整 `--min-companies` 和 `--min-jobs`。验证失败时先修正数据，不得跳过错误继续交付。

## 能力边界

完成完整任务需要：

1. 读取简历或用户背景。
2. 联网检索并打开招聘来源。
3. 创建或编辑 `.xlsx` 文件。

缺少某项能力时，明确说明受阻环节。不得把搜索摘要直接当作官方岗位信息，也不得用 Markdown 表格冒充 Excel 交付物。

## 工作模式

- **新建模式**：没有旧追踪表，创建精简工作簿。
- **增量更新模式**：在旧文件副本上更新，保护用户填写内容。
- **旧版精简模式**：将旧版多工作表、多重复列结构迁移为本 Skill 的四张主表。
- **仅企业池模式**：只建立企业池，不强制核验具体岗位。
- **重点核验模式**：用户已有企业名单，只核验岗位。

# 完整工作流程

## 第1步 读取输入并确定范围

完整读取简历、旧表和用户限制，提取：

- 预计毕业年月、学历和专业
- 实习、科研、项目、证书和技能证据
- 目标岗位、行业和城市
- 可接受的销售、轮岗、出差、倒班、异地和调剂条件
- 明确排除的岗位、行业和地区

只在缺失信息会明显改变检索结果时询问一个简短问题。能够从材料确定的信息不得重复询问。次要缺失项使用明确标注的默认假设，不得虚构偏好。

## 第2步 判断招募届别

按预计毕业年份判断届别。例如预计 2027 年毕业，默认搜索“2027届校园招聘”，即使公告发布于 2026 年。

研究数据中分开保存招募届别、发布日期、开放日期、截止日期和核验日期。Excel 只展示对用户有直接价值的截止日期和核验信息，其他日期保留在 JSON 底稿中。

## 第3步 建立100至150家真实企业池

除非用户要求更小范围，默认建立 100 至 150 家不重复企业。企业池允许包含大型集团、中型企业、小型企业和初创企业，不得因规模小自动排除。

企业池每行只代表一家企业，Excel 只保留九列：

1. 企业名称
2. 企业性质及规模
3. 行业
4. 主要地区
5. 适配岗位方向
6. 企业优先级
7. 核验状态
8. 招聘官网
9. 招聘线索与风险备注

中小企业的规模依据、信息透明度、招聘稳定性和风险原因合并写进“招聘线索与风险备注”，不再拆成多列。规模无法确认时写“规模待确认”。规模小本身不能作为高风险的唯一理由。

## 第4步 深度核验30至50家高匹配企业

根据简历证据、企业优先级和岗位方向，优先深度核验 30 至 50 家企业。条件允许时可扩大范围，但不得用往年岗位或搜索摘要冒充当前开放岗位。

其余企业保留在企业池，状态标为待核验、已核验暂无岗位或待复核。候选企业数、已核验企业数和岗位数必须分开统计。

## 第5步 联网核验具体岗位

按照 `references/research-rules.md` 执行。研究 JSON 可以保存完整来源和状态依据，Excel 的岗位清单只展示十三个用户决策字段：

1. 企业名称
2. 岗位名称
3. 工作地点
4. 招聘状态
5. 截止日期
6. 核心工作内容
7. 硬性要求及判断
8. 薪资福利或岗位质量
9. 契合指数
10. 匹配点与主要门槛
11. 当前行动
12. 招聘链接
13. 来源等级及核验日期

薪资、福利、团队、工作强度和成长路径只有来源明确或用户在面试中取得信息时才填写。未披露时留空或在同一单元格简短说明，不得新增多列“待确认”。

## 第6步 计算契合指数和当前行动

只对取得具体岗位或明确岗位类别的记录，按 `references/matching-rubric.md` 计算 0 至 100 分。

不再同时输出推荐层级、处理顺序和是否立即投递。统一使用“当前行动”：

- 立即投递
- 本周投递
- 继续核验
- 持续关注
- 暂不处理

“匹配点与主要门槛”使用一至三句具体证据，避免重复整份简历。

## 第7步 验证结构化数据

将企业池和岗位记录写入 JSON，运行 `validate_tracker_data.py`。修正：

- 重复企业
- 重复岗位记录ID
- 非法状态
- 活跃岗位缺少有效来源
- 日期格式错误
- 分数越界
- 招聘状态与当前行动明显冲突
- 不满足硬性条件却标为立即投递

完整研究字段保留在 JSON，不要求全部写入 Excel。

## 第8步 创建或更新精简工作簿

新建模式只保留四张主工作表：

1. **求职总览**
2. **企业池**
3. **岗位清单**
4. **投递进度**

不得默认再建立背景诊断、招募节奏表、字段选项和更新日志四张独立表。

- 背景优势、限制和搜索边界压缩到“求职总览”。
- 招聘节奏压缩到总览的简短提醒区。
- 下拉选项直接写入数据验证，不为此创建可见设置表。
- 更新记录仅在用户明确需要审计日志时增加。

“投递进度”只加入用户准备投递或已经投递的岗位。不得把所有已核验、已截止或从未准备投递的岗位机械复制进投递表。

## 第9步 安全执行增量更新

1. 先复制原文件，在副本上修改。
2. 企业池按标准化企业名称去重。
3. 岗位按内部记录ID匹配。记录ID通常由企业、届别、项目、岗位和地点组成，可放在岗位表最右侧的窄技术列。
4. 自动更新招聘状态、截止日期、链接和核验信息。
5. 不覆盖用户填写的投递日期、简历版本、当前环节、联系人、复盘和备注。
6. 已截止岗位保留在岗位清单并改为“暂不处理”，但不自动加入投递进度。
7. 旧版表迁移时，先合并重复列，再删除空表和纯后台表。

## 第10步 最终检查

交付前检查：

- 企业池是否达到用户要求，且不存在明显重复企业
- 深度核验企业和岗位数量是否分别统计
- 企业池是否只有公司层信息
- 岗位清单是否没有重复行业、规模、企业发展阶段等公司静态信息
- 岗位清单是否没有同时存在推荐层级、处理顺序和是否立即投递等重复优先级字段
- 投递进度是否只含准备投递或已经投递的岗位
- 活跃岗位是否有可追溯链接和核验日期
- 记录ID是否唯一
- 日期是否为真实日期值
- 公式是否出现 `#REF!`、`#VALUE!`、`#DIV/0!`、`#NAME?`
- 总览统计是否正确，未来7天截止显示为数量而非日期
- 用户人工字段是否未被覆盖
- 导出的 `.xlsx` 能重新打开并读取关键区域

只有实际使用 WPS 打开测试过，才可声称“已验证 WPS 兼容”。否则说明采用常规 `.xlsx` 兼容写法，未进行 WPS 实机验证。

## 最终交付

提供：

1. 可下载的 `.xlsx` 文件。
2. 候选企业数、已核验企业数、岗位数和当前可投岗位数。
3. 最值得处理的岗位，最多 10 项。
4. 最契合的岗位类别，最多 5 类。
5. 信息核验截止日期。
6. 仍需复核的重点企业或岗位。

不得编造招聘信息。无法核实的内容标记为待核验、待复核、已核验暂无岗位或未披露。
